## 1. Abstract & Theoretical Foundations

In contemporary computer science, the classical equivalence:
$$\text{Performance} \equiv \frac{1}{\text{Execution Time}}$$
is incomplete. Modern data centers, mobile devices, satellites, and embedded edge systems are fundamentally **energy- and thermally-constrained**. 

A compiler optimizing solely for cycle count or instruction count can paradoxically produce binaries that consume *significantly more total electrical energy* and induce severe thermal throttling.

Rubix establishes an **Energy-Aware Compilation Model** based on three foundational principles:
1. **The DRAM Energy Dominance Principle**: Moving data across the memory bus (off-chip DRAM) consumes 100x to 10,000x more picojoules per bit than executing ALU operations. Minimizing memory traffic is the single most effective energy optimization.
2. **The "Race-to-Sleep" Tradeoff**: While completing work rapidly allows CPU cores to enter low-power C-states (C6/C7), aggressive speculative execution, wide SIMD units (AVX-512/AMX), and elevated clock frequencies (DVFS overdrive) cause power consumption to scale super-linearly ($P \propto V^2 f$).
3. **Green Intermediate Representations**: By preserving affine lifetime bounds and lexical regions in AIR, the compiler avoids heap allocations and DRAM write-backs, keeping data resident in energy-efficient registers and L1 cache lines.

## 2. Microarchitectural Energy Breakdown

### 2.1 The Instruction Count Fallacy
A long-standing assumption in 1990s compiler theory was that fewer instructions automatically translated to lower power consumption. 

2025–2026 empirical studies on modern out-of-order processors (Intel Raptor Lake / Arrow Lake, AMD Zen 4 / Zen 5, Apple M3 / M4) demonstrate that:
* **Micro-op Fusion and Zero-Latency Moves**: Processors handle register renames and scalar register-to-register moves entirely in the rename stage with virtually zero dynamic power dissipation.
* **Vector Execution Energy Penalties**: Spinning up 512-bit vector units (AVX-512) or matrix engines requires voltage elevation across large die areas. If vector loop trip counts are low ($N < 16$), the thermal and energy cost of activating the vector unit exceeds the energy consumed by a clean scalar loop with 32 general-purpose registers (Intel APX).

### 2.2 Memory Subsystem Energy Consumption
Empirical measurements across DDR4, DDR5, and LPDDR5X memory architectures demonstrate:

| Memory Operation | Typical Latency | Energy per 64-bit Word | Relative Energy |
|:---|:---|:---|:---|
| **Register Access** | 0–1 cycles | $\approx 0.05\text{ pJ}$ | $1\times$ |
| **L1 Data Cache Hit** | 4–5 cycles | $\approx 0.8\text{ pJ}$ | $16\times$ |
| **L2 Cache Hit** | 12–14 cycles | $\approx 4.5\text{ pJ}$ | $90\times$ |
| **L3 Cache Hit (Shared)** | 40–60 cycles | $\approx 25\text{ pJ}$ | $500\times$ |
| **DRAM Read (Page Hit)** | 45–65 ns | $\approx 650\text{ pJ}$ | $13,000\times$ |
| **DRAM Read (Page Miss / Bank Conflict)** | 90–120 ns | $\approx 1,800\text{ pJ}$ | $36,000\times$ |

**Conclusion**: Eliminating a single off-chip DRAM page miss saves sufficient electrical energy to execute approximately **18,000 to 36,000 ALU instructions**.

## 3. Contemporary 2025–2026 Research

Recent compiler advancements have codified energy as an explicit objective:
* **Lexicographic Reward Models (e.g., KernelPro, 2025–2026)**: Machine-learning guided code generators utilize multi-objective reward functions balancing instruction count, memory bandwidth, and thermal dissipation.
* **Dynamic Variant Selection (OpenMP / ASCENDER, 2025–2026)**: Runtime systems dynamically select code variants generated by the compiler based on real-time power caps (`RAPL` / Running Average Power Limit on x86, Apple Energy Counters).
* **Heterogeneous Memory Compilers (2025–2026)**: Compilers partition data between on-chip high-bandwidth SRAM and transient DRAM based on static escape and lifetime analysis.

### 4.1 Escape Analysis & Stack Promotion
In [compiler/middle/escape_analysis.bix](file:///home/bishwaxyz/translator/rubix/compiler/middle/escape_analysis.bix) and [compiler/middle/air.bix](file:///home/bishwaxyz/translator/rubix/compiler/middle/air.bix):
* Objects whose lifetime is statically confined to the lexical scope are promoted via `AIR_OP_STACK_PROMOTE`.
* Stack promotion ensures memory accesses hit the hot L1 cache (L1D) without incurring operating system page faults, memory management locking, or memory bus writes.

### 4.2 Exploiting Extended General Purpose Registers (APX & Arm64)
* The Rubix hardware model targets 32 general-purpose registers on architectures supporting them (Intel APX, Arm64, RISC-V).
* Doubling available registers from 16 to 32 reduces spill/reload instructions to the stack by up to **25%**, directly eliminating cache line round-trips and associated switching power.

### 4.3 Pure Algebraic Dead-Code Elimination (DCE)
* In [compiler/middle/effect_optimizer.bix](file:///home/bishwaxyz/translator/rubix/compiler/middle/effect_optimizer.bix):
* Functions proven `EFFECT_PURE` whose return values are unconsumed are completely purged at compile time. Zero instructions emitted $\implies$ zero energy consumed.

## 5. Empirical Metrics & Measurement Protocol

To ensure energy claims are mathematically grounded, Rubix benchmarks employ:
1. **Linux `perf` Hardware Counters**:
   * `power/energy-pkg/`: Total processor package energy in Joules.
   * `power/energy-ram/`: Total DRAM controller energy in Joules.
   * `cache-misses`: L3 cache misses as an indirect proxy for DRAM transaction energy.
2. **Joules Per Operation ($J/\text{op}$)**:
   $$\text{Energy Efficiency} = \frac{\text{Total Package Energy (Joules)}}{\text{Total Operations Completed}}$$

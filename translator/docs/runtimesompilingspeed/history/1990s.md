# Computing and Optimization History: The 1990s & The Superscalar / Dynamic Era

## 1. Hardware Architecture & Physical Constraints
* **Representative Systems**: Intel Pentium (1993, dual-issue in-order), Intel Pentium Pro (1995, P6 microarchitecture, out-of-order execution), MIPS R10000 (1996), DEC Alpha 21264 (1998, 4-way superscalar out-of-order), PowerPC 604, Sun UltraSPARC.
* **Technological Shifts**:
  * **Dynamic Out-of-Order (OoO) Superscalar Execution**: Processors no longer executed instructions in the rigid order produced by the compiler. Using dynamic register renaming (RAT/ROB/Reservation Stations derived from Robert Tomasulo’s 1967 algorithm), the CPU discovered instruction-level parallelism (ILP) at runtime across data dependencies.
  * **Two-Level Adaptive Dynamic Branch Prediction (Yeh & Patt, 1991–1993)**: Branch prediction accuracy jumped from ~80% (static direction heuristics) to 95%+, allowing deep speculative execution.
  * **The "Memory Wall" (Wm. A. Wulf & Sally A. McKee, 1995)**: CPU clock frequencies accelerated by ~60% per year, while DRAM cycle times improved by only ~7% per year. A memory access that cost 5–10 CPU cycles in 1985 cost 100–300 CPU cycles by the late 1990s.

---

## 2. What Was Expensive?
* **L2 / Main Memory Cache Misses**: Missing the cache stalled an entire pipeline for dozens to hundreds of clock cycles. CPU designers had to add large on-package or on-die L2 caches.
* **Branch Mispredictions**: Pipelines deepened to 10–14 stages. A mispredicted branch flushed the entire pipeline, dumping 10–20 clock cycles of speculative work down the drain.
* **Virtual Method Dispatch (C++, Java, Smalltalk, Self)**: Deep object hierarchies and polymorphism caused indirect call instructions (`CALL [EAX + offset]`), defeating static branch prediction and instruction prefetching.

---

## 3. What Was Slow?
* **Pure Static Compilers on Dynamic Code**: Compilers could not predict which polymorphic method would be invoked or which branch would be taken without runtime data.
* **Object-Oriented Runtimes & Garbage Collection**: Early Java 1.0 (1995) was an interpreted stack machine, running 20 to 50 times slower than compiled C/C++.

---

## 4. What Programmers Optimized Manually
* **Data Structure Packing for Cache Lines**: Grouping related struct members together so they fit in a single 32-byte or 64-byte L1 cache line.
* **Loop Tiling / Cache Blocking**: Manually rewriting matrix multiplications and nested loops into square sub-blocks to fit within the L1/L2 cache.
* **Avoiding Virtual Functions in C++**: Using templates and static polymorphism to avoid virtual function table (`vtable`) indirect dispatch overhead.

---

## 5. What Compilers Optimized Automatically
* **Static Single Assignment (SSA) Form Formalization (Cytron, Ferrante, Rosen, Wegman, & Zadeck, 1991)**:
  * Cytron et al. published the seminal algorithm for placing minimal $\phi$ (phi) functions using dominance frontiers in $O(E)$ time.
  * SSA separated variable versions ($x_1, x_2$), turning def-use chains into explicit graph edges and rendering global value numbering, dead code elimination, and constant propagation orders of magnitude faster and cleaner.
* **Sparse Conditional Constant Propagation (SCCP) (Wegman & Zadeck, 1991)**: Simultaneously propagated constants while pruning unreachable conditional branches in a single unified lattice pass over SSA form.
* **Profile-Guided Optimization (PGO / FDO)**: Compilers (e.g., GCC, DEC Alpha GEM, IBM XL) instrumented code to measure branch execution counts and call edge frequencies during a test run, re-compiling the binary with basic-block reordering, function inlining, and loop unrolling biased strictly toward the measured hot paths.
* **Global Value Numbering (GVN)**: Eliminating redundant algebraic expressions across complex CFGs in SSA form.

---

## 6. The Shift from "Compiler Knows Everything" to Dynamic Hardware and Runtimes
Prior to the 1990s, the dominant philosophy (VLIW, early RISC) assumed that:
> *"The compiler has unlimited time to analyze the whole program and understands every dependency; hardware should be as dumb and fast as possible."*

The 1990s proved this assumption fundamentally false for three reasons:
1. **Dynamic Memory Latency**: A static compiler cannot know whether a memory load will hit the L1 cache (1 cycle), hit the L2 cache (10 cycles), or miss to DRAM (200 cycles). A static instruction schedule that stalls on an unexpected cache miss freezes the entire processor. An out-of-order CPU simply executes other independent instructions around the stall.
2. **Dynamic Aliasing**: Static alias analysis in languages with pointers (C/C++) is undecidable in general. Compilers must be conservative. The hardware load/store queue dynamically disambiguates addresses at the clock-cycle level.
3. **Polymorphic / Dynamic Languages**: In languages like Smalltalk, Self, and Java, target method types are not known until runtime.

---

## 7. The JIT Revolution: Self and HotSpot Lineage
At Stanford and Sun Microsystems, David Ungar, Craig Chambers, and Urs Hölzle transformed runtime systems:
* **Self-91 & Strongtalk (Chambers, Ungar, Hölzle, 1989–1994)**:
  * Proved that a pure dynamic language with late binding could reach C-like speeds.
  * **Inline Caching & Polymorphic Inline Caches (PICs)**: Replacing indirect vtable dispatch with direct branch comparisons cached at the call site.
  * **Speculative Inlining**: Inlining the target method based on the assumption that 99% of calls go to the same concrete type.
  * **Deoptimization & Uncommon Traps (Hölzle, Chambers, Ungar, 1992)**: The runtime could optimize aggressively under speculative assumptions. If an assumption was invalidated (e.g., a new class was loaded), the compiled native code safely reconstructed the interpreter stack frames on the fly and continued in the interpreter without crashing.
* **Java HotSpot (1997–1999, Longview Technologies / Sun)**: Urs Hölzle and team brought Self's techniques into Java, introducing **Tiered Compilation** (fast interpreter/C1 client compiler for instant startup, profiling method invocations, and C2 Server compiler with aggressive global SSA optimizations for hot methods).

---

## 8. Breakthrough That Changed Compiler Design
* **SSA Form Standardized (Cytron et al., 1991)**: Made complex interprocedural and global optimizations practical in production compilers.
* **LTO / Whole-Program Analysis**: Compilers began preserving intermediate representations until link-time to perform cross-module inlining and dead-code elimination.

---

## 9. Ideas That Survived
* SSA form (used by GCC, LLVM, HotSpot, V8, Rust, Go).
* Out-of-Order hardware execution (standard across all modern high-performance x86, ARM, and RISC-V cores).
* Dynamic branch predictors (branch history registers, two-level predictors).
* Polymorphic Inline Caching (PICs).
* Speculative inlining with deoptimization.

---

## 10. Ideas That Disappeared
* **Pure Static VLIW for General Computing (Intel Itanium / IA-64)**: Conceived in the late 1990s, Itanium attempted to replace OoO hardware with compiler-directed EPIC (Explicitly Parallel Instruction Computing). It proved that static compilers could not handle unpredictable memory latencies, leading to IA-64’s eventual demise.

---

## 11. Ideas That Returned Decades Later Under a Different Name
* **Self's Adaptive Optimization**: Direct parent of modern JavaScript engines (V8, JavaScriptCore, SpiderMonkey) and modern JVMs (GraalVM).
* **Tomasulo Dynamic Scheduling**: Scaled up from 16 reservation stations in 1995 to 500+ entry Reorder Buffers in 2026.
